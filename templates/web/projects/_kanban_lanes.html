{% load i18n %} {% load lucide %} {% load web_extras %} {% comment %} The board sliced into lanes — one row per milestone or per epic, the status columns running across the top once. A lane is a cut across the same columns, not a different board: the cell at the crossing holds the work of that status in that milestone. Moving a card sideways changes its status, as everywhere. Moving it DOWN is refused: each lane is its own Sortable group (see ``initKanbanDnD``), so a card cannot be dropped into another milestone by brushing past it. Attaching work to a date is a deliberate act — the task rail, the bulk bar, or the milestone's own page. Column collapse is deliberately absent here. It is a per-status preference that would have to hold across every lane at once, and a board with a dozen lanes has enough state to read already. {% endcomment %}
{% comment %} The columns, named once at the top of the board. Every grid here flows by column with auto tracks rather than a fixed count: the backlog toggle hides the ``planned`` / ``ready`` columns outright (acta.js, keyed on ``data-kanban-column``), and a fixed track count would leave their width behind as a gap. The rows are flex, not grid, and the columns have no minimum width, so the board always fits its pane and never scrolls sideways. That is the point: a lane's header is one row spanning the whole board, and the moment the board is wider than the pane that header stops matching it — its right-hand rollup lands in the middle of the last column instead of at the end. Narrow columns are the better trade, and the card clips rather than reflows. Flex also gives us the collapse the plain board has: clicking a column chip folds that status to a strip in the header AND in every lane at once, because both rows read the same per-status store. A grid of auto tracks could not do that — every track is the same width by definition. {% endcomment %}
