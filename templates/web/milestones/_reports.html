{% load i18n %} {% load lucide %} {% load web_extras %} {% comment %} The two questions that keep a milestone's membership honest. Expects ``milestone`` and ``reports`` from ``apps.milestones.services.membership_reports``. Both read off data the product already holds, and neither ever joins a task to anything on its own — they are questions, and a person answers them. *Near, not in* catches the slip of the hand: work due before the date that nobody committed. *Blocks, not in* is the valuable one: it finds a hole in the plan, and the worst case it names — a blocker scheduled after the work it blocks — is invisible everywhere else. Nothing here appears on a closed milestone: it is a record by then, and nothing can be missing from it any more. {% endcomment %} {% translate "Add" as add_label %} {% translate "Move here" as move_label %} {% if reports.near or reports.blocks %} {% comment %} Side by side the two reports are rarely the same length, so each caps its own height and scrolls its own rows while the grid stretches both to the same box.
