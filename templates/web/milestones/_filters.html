{% load i18n %} {% load lucide %} {% load web_extras %} {% comment %} The list's filters, served by the server. The page used to carry none — a dozen dates grouped by month was its own navigation. A workspace that plans properly outgrows that, and three of the four things worth filtering on (state, risk, progress) are read off the attached work rather than stored, so the narrowing happens in Python over rows already built rather than in a query that would have to learn to derive them. Server-side, not client-side like the task dock: hiding rows in the DOM would leave the month headers, their counts and the "past" fold all describing a list that is no longer there. Each chip carries the count it would leave, taken against the unfiltered rows so the numbers hold still while someone clicks through them. Expects ``facets`` and ``chosen`` from ``milestones_overview``. {% endcomment %} {% comment %} The swap contract sits here once and every chip inherits it: a filter redraws the list, not the page. ``hx-select`` picks the fresh ``#milestones-body`` out of the full response, so the view stays a plain view with no HTMX branch in it. ``data-push-href`` on ``#milestones-body`` is what moves the URL. htmx's own history is off app-wide (ADR 0024 — acta.js runs its own router), so ``hx-push-url`` is a no-op here; acta.js watches for the marker and pushes the clicked link's href, which is what keeps the narrowed list alive through a refresh and reachable with Back. Each chip keeps its ``href`` as well, so middle-click and a JS-less load still work — ``hx-get`` only intercepts the ordinary click. {% endcomment %}
